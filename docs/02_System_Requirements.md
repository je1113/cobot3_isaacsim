# ✏️ 2. System Requirements

> Isaac Sim_협동3 / 24.04+5.x / Development Process / 2. System Requirements

**이 단계의 핵심**
비즈니스 목표를 **시스템이 제공해야 할 구체적인 기능 단위로 변환**하는 것입니다.
**"무엇을 만들 것인가"** 를 시스템 관점에서 정의합니다.

> **반도체 후공정 부품 캐리어 자동 이송·피킹 시스템 — 디지털 트윈 기반 사전 검증**
> 스토커 랙의 트레이/매거진을 인식 → 파지 → AMR 이송 → 테스트 핸들러/패키징 스테이션 배치 → 충전 도킹까지 무인 풀사이클

---

## 1. 시스템 구성

> 프로젝트에 사용할 **로봇, 센서, 환경, 하드웨어**를 결정합니다.
> "왜 이것을 선택했는가" 를 함께 기록하면 리뷰 시 판단이 명확해집니다.

| 항목 | 정의 내용 | 선택 · 역할 | 왜? (선택 이유) |
|---|---|---|---|
| **환경 타입** | 어떤 공간인가 | **반도체 후공정 팹 클린룸** — 스토커(트레이 랙) 존 — 통로 — 테스트 핸들러 / 패키징 스테이션 — 충전 도킹 스테이션으로 구성된 라인 일부 | 사람이 트레이를 옮기던 구간(스토커 ↔ 장비)이 그대로 검증 대상이며, 랙 슬롯 높이·통로 폭·장비 앞 정지 위치를 바꿔가며 레이아웃을 비교할 수 있도록 모듈형으로 구성 |
| **이송 대상** | 물체 종류 + 규격 | **JEDEC 트레이 / C-tray / 매거진** 3종을 기본 모델로 준비. JEDEC 매트릭스 트레이 표준 외형(약 322.6 × 135.9 mm, 두께 7.62 / 12.7 mm) 기준, C-tray는 고객 규격 가정, 매거진은 튜브형 적층 케이스 | 파지 성공률을 "트레이 종류별"로 집계하는 것이 프로젝트 목표이므로, 형상·질량·파지면이 다른 3종을 처음부터 분리 정의 |
| **매니퓰레이터** | 종류 + 역할 | **Franka Panda (7축) + Franka Hand 평행 그리퍼** — 랙 슬롯의 트레이 **인식 → 접근 → 파지 → 리프트 → AMR 적재 / 스테이션 배치** 담당 (핵심 파지 단계) | Isaac Sim 5.x 기본 제공 자산으로 그리퍼·모션 제어 예제가 풍부해 파지 검증에 바로 집중할 수 있고, 7축 여유 자유도로 좁은 랙 슬롯에 대한 접근 자세를 확보하기 쉬움. 실물 협동로봇(예: Doosan M 시리즈)으로의 교체는 sim-to-real 단계에서 검토 |
| **주행 로봇** | 종류 + 역할 | **Nova Carter (AMR)** — 매니퓰레이터를 상부에 탑재한 **모바일 매니퓰레이터** 베이스. 스토커 ↔ 스테이션 간 **트레이 운반**, 장비 앞 정위치 정렬, 작업 종료 후 **충전 스테이션 도킹** 담당 | Isaac Sim 기본 AMR로 LiDAR·카메라가 내장되어 주행·도킹 예제를 그대로 활용 가능. 1차 마일스톤은 매니퓰레이터를 고정 배치해 파지만 먼저 검증하고, 2차에 AMR 탑재로 통합 |
| **센서** | 종류 + 위치 | **RGB + Depth 카메라 ①** 매니퓰레이터 손목(eye-in-hand) — 트레이 종류·ID·자세 인식, 파지점 산출<br>**RGB + Depth 카메라 ②** 스토커 랙 상단 고정 — 슬롯 점유 여부와 트레이 대략 위치 1차 탐색<br>**2D LiDAR** Nova Carter 내장 — 통로 주행, 장애물 회피, 스테이션·충전 도킹 정렬 | 랙 안쪽 트레이는 고정 카메라만으로는 가려지기 쉬워 손목 카메라로 근접 확인이 필요하고, 고정 카메라는 "어느 슬롯에 무엇이 있는가"를 한 번에 파악해 탐색 시간을 줄임. 주행·도킹은 AMR 내장 센서로 충분 |
| **PC 구성** | 대수 + 역할 | **GPU PC A (시뮬)** Isaac Sim 실행 — 팹 환경·트레이 스폰, AMR 주행, 매니퓰레이터 제어, 물리·충돌 판정, 카메라 이미지 송신<br>**GPU PC B (비전)** 인식 모델 추론 — 트레이 종류/ID 검출, 카메라 기준 3D 좌표·자세 산출<br>**개인 PC (변환·오케스트레이션)** 카메라 → world → 로봇 base 좌표 변환, 이송 지시(트레이 ID ↔ 목적지) 관리, 시행 결과·성공률 로그 집계 | 시뮬 렌더링과 비전 추론이 GPU를 동시에 점유하면 프레임이 떨어지므로 분리. 좌표 변환·오케스트레이션은 연산이 가벼워 개인 PC에서 처리하며, 실패 원인을 단계별로 분리 확인하기 쉬움 |
| **실행 환경** | OS + 시뮬레이터 | **Ubuntu 24.04 / Isaac Sim 5.x** | 과정 표준 환경. PC 3대가 같은 네트워크에서 이미지·좌표·명령을 주고받는다 |

### 구성 배치도 (시뮬레이션 환경)

```
┌──────────────────────────┐    ┌──────────────────────────────┐    ┌──────────────────────────┐
│ 🗄️ 스토커 존              │    │ 🧪 테스트 핸들러 / 패키징     │    │ 🔋 충전 도킹 스테이션      │
│ 트레이 랙(다단 슬롯)      │ ⟶ │    스테이션                   │ ⟶ │ 도킹 마커, 충전 패드       │
│ 고정 RGB-D 카메라 ②       │    │ 입력 슬롯(배치 위치)          │    │                          │
│                          │    │ 장비 앞 정지 마커             │    │                          │
│ → 트레이 인식 · 픽업      │    │ → 트레이 배치 · ID 확인       │    │ → 도킹 · 사이클 종료       │
└──────────────────────────┘    └──────────────────────────────┘    └──────────────────────────┘
```

모바일 매니퓰레이터(Nova Carter + Franka Panda, 손목 RGB-D ①, 내장 LiDAR)가 세 존을 순회한다. 통로 폭·랙 높이·정지 위치는 변수로 두어 레이아웃 비교에 사용.

### 단계별 입력 · 출력 요약

| 단계 | 입력 | 출력 | 담당 |
|---|---|---|---|
| 이송 지시 발행 | 스토커 재고(트레이 ID, 슬롯), 스테이션 요청 | 작업 큐 (트레이 ID → 목적지) | 개인 PC |
| 스토커로 주행 | 목표 랙 위치, LiDAR | 랙 앞 정위치 도달 신호 | GPU PC A |
| 트레이 인식 | rgb + depth + tf | 트레이 종류, ID, 카메라 기준 3D 위치·자세 | GPU PC B |
| 좌표 변환 | 카메라 기준 좌표, tf | 로봇 base 기준 파지점·접근 자세 | 개인 PC |
| 픽업 | 파지점·접근 자세 | 트레이 AMR 적재 완료, 파지 성공 여부 | GPU PC A |
| 스테이션 주행 · 배치 | 목적지, 입력 슬롯 위치 | 배치 완료 신호, 배치 위치 | GPU PC A |
| 배치 검증 · 기록 | 배치 위치, 트레이 ID | 오배송 여부, 사이클 타임, 시행 로그 | 개인 PC |
| 도킹 | 도킹 마커, LiDAR | 도킹 완료 · 충전 상태 | GPU PC A |

> 📌 **반복 검증 시 변경하는 변수** — 트레이 종류(3종), 랙 슬롯 높이, 트레이 놓임 자세(치우침·기울어짐), 조명, AMR 정지 위치 오차. 각 시행은 위 플로우를 처음부터 끝까지 수행하고, 「배치 검증 · 기록」 단계에서 성공 여부와 사이클 타임을 남긴다.
